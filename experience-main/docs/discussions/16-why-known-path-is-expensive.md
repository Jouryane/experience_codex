# 16 · 为什么"有成功经验反而更贵"——结构性诊断

> 2026-09-18。四轮负结果之后的反思。**不是收缩边界，是找问题点。**
> 前置：[13](13-ab-paired-result.md) / [14](14-long-prefix-result.md) / [15](15-interleaved-repair-result.md)。

## 一、先撤回两件测量问题（在解释现象之前必须先修尺子）

**撤回一｜`model_tool_calls` 是坏指标。**
round 15 里 off 臂恒为 0，而基线**必然**发过工具调用（它跑过 `check.py`、改过文件）。
真相是：这个计数器只匹配带 "tool" 字样的 item，于是它**只数到了 `dynamicToolCall`**，
根本不是"模型自己的工具调用"。**15 §二 里用它做的论证作废。**

**撤回二｜`model_requests` 从未被验证。**
它数的是 `thread/tokenUsage/updated` 通知条数。但看 round 14：
**一个 52 操作的任务，基线只用了 2–3 次"请求"**。
要么基线真的这么强，要么这个计数器数的不是模型调用次数。
**四轮结论全部建立在这个未验证的量上**——这是方法上的硬伤，必须先修。

## 二、结构性诊断：判断权留在了模型一侧

现在回答你的问题：**为什么一条已经成功过的路径，复刻时反而更贵？**

RFC 式的说法：

> 在 Pull 模式下，**"这条经验适不适用"的判断权在模型手里**，
> 而模型完成这个判断所需要的成本，**约等于它自己把这件事做一遍的成本**。

机理逐步展开：

1. 我们的 runtime **能**在执行前验证前提——但它只有**在模型已经决定调用之后**
   才有机会验证；
2. 模型要决定"调不调"，必须**先知道当前状态是否符合经验的前置条件**；
3. 而获取这个"知道"的唯一途径，是**探索**——跑检查、读文件、看输出；
4. 于是模型花掉了和"自己做"一样多（甚至更多）的步骤，去**确认该不该委托**。

**我们省掉的是"执行"，没有省掉"判断要不要执行"。而在小任务里，判断就是全部成本。**

这不是 Pull 的实现没做好，而是 Pull 与 Push 的**结构差异**：

| | 谁观察世界 | 谁做匹配判断 | 对模型而言的判断成本 |
|---|---|---|---|
| **Push** | runtime | runtime | **零** |
| **Pull** | 模型 | 模型 | **≈ 自己做一遍的成本** |

## 三、四轮数据在这个诊断下重读

| 轮次 | 任务文本是否已给出状态 | 执行是否可批处理 | 结果 | 与诊断是否一致 |
|---|---|---|---|---|
| 13 | **是**（文本里就是文件清单） | 是（4–5 个写操作） | 3/4 微正、不显著 | 一致（判断免费，但执行也没空间） |
| 14 | **是** | 是（52 个写操作压成 1 次调用） | 0/3 | 一致（判断免费，执行被批处理吃掉） |
| 15 | **否**（要看工作区才知道坏在哪） | 否（必须交错运行） | 0/2 | 一致（判断不免费 → 直接归零） |

**四轮的方向全部被"判断成本"这一列解释。** 我们此前把注意力放在"执行步数"上，
而真正的控制变量是**判断成本**——它我们一次都没有主动设计过。

## 四、更不舒服的推论：Pull 的收益格可能是**空的**

把两个条件摆成矩阵：

| 判断成本 | 执行成本 | Pull 有收益吗 |
|---|---|---|
| 低 | 高 | **理论上应该有——但这一格我们没测到** |
| 低 | 低 | 无（14） |
| 高 | 高 | 无（15） |
| 高 | 低 | 无（13 边缘） |

问题在那一格是否**存在**：

- "判断成本低"意味着**任务文本已经把当前状态说清楚了**；
- 而状态一旦被说清楚，**要做的动作通常也就被说清楚了**——
  因为动作就是这个状态的函数；
- 那么它大概率**可以被一次批处理调用完成**（14 已经证明 52 个写操作只要 2–3 次请求）；
- 反过来，若执行成本高（必须交错运行、看结果才能决定下一步），
  那任务文本就**无法**预先说明状态 → 判断成本必然高。

**两条合起来：`判断成本低 ∧ 执行成本高` 这一格可能是空的。**
如果它是空的，那么 **Pull 这条腿在"省成本"这个目标上天然没有可展示的成功**——
不是我们没测好，是这个配置本身自相矛盾。

**这是一个假说，不是结论。** 但它比"再换一种任务形状试试"更有解释力，
而且它是**可证伪的**：只要能构造出一个任务，其
① 状态由任务文本完全给出、② 基线**无论如何**都要发多次工具调用，
那么这个假说就被推翻。

## 五、因此下一步不是收缩边界，而是三件事

1. **先修尺子**：证明 `model_requests` 等于模型调用次数（用 assistant-message 数
   或 `last.inputTokens` 交叉验证）；重写"模型自己的工具调用"计数器，
   按 item 类型分别统计（`commandExecution` / `fileChange` / `dynamicToolCall`）。
   **尺子不修，后面所有数字都不可信，包括我们打算对外的那些。**
2. **直接构造第四节的空集测试**：设计一个"文本给全状态、但基线无法批处理"的任务。
   能构造出来 → Pull 还有戏；构造不出来 → 得到一条强得多的结论。
3. **不要动主张**：如果结论是 Pull 打不出成本优势，那**正确的回应不是把边界收窄到
   "我们只在能赢的地方用"**，而是回到 [03](03-host-value-argument.md) §五——
   experience 真正卖的是**结构属性**（可审计、可回滚、副作用前拒绝），
   那些不需要在速度上打赢基线。**Pull 腿的价值论证应该换锚点，而不是缩小范围。**
