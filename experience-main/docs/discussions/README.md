> 目的：把基于当前 experience 建设结果的多轮讨论中**经过协商确定**的思想留存下来。
> 只留确定的结论；被协商否定的不留正文，但登记在索引里，避免重复讨论。

## 三条纪律

1. **本目录是思想留档**，不是开发计划，也不承诺实现。任何一条进入实现前，
   仍走既有纪律：脚本/fixture 先行 → 实现 → `cargo test` 全绿 → 真机 ≤2 →
   产物与 fixture 同步。
2. **只留确定内容**；被否定的登记在索引，不写正文。
3. **【2026-09-17 新增】外部输入进来时，先重评已有段落，再新增。**
   这一轮的教训是：外部回复的价值有一半不在它说了什么，而在它让哪些旧段落
   变成了无用的东西。本目录是逐轮 append 出来的，每一节都只被写过一次——
   按实验 E9 的说法，这些就是 `pass_count = 1` 的段，需要按通过量而非条数保留。

## 为什么单开一个目录

现有 docs 分三类：现状说明（product-overview / usage-guide）、可执行契约
（learning-reuse-contract / computer-use-adapter-contract / scale-index-design）、
开发账本（README 的历史记录）。

本目录回答第四类问题：**我们为什么这样理解经验**——包括尚未落地、
甚至与现有实现相冲突的定性判断。这类内容混进契约文档会让契约失去可执行性。

## 未决问题（不当作结论使用）

- **U1｜经验库是一个“库”还是一个“协议”**：段一旦跨会话、跨项目，
  “段的有效性由谁记账”会分叉——Experience 自持跨会话证据库，
  还是让宿主的会话日志去投影？这决定协议的边界。
- **U2｜先天经验的发布形态**：随宿主版本、随模型版本，还是独立可更新的经验包？
- **U3｜记忆增长策略**：段化只把存储从“按任务复制”降到“按步骤记账”，
  增长仍是线性的。真正的答案是**保留策略**，候选方向是“按通过量保留”。
- **U4｜经验进入中枢的判据**：见 01 的“待确认”条目（识别不确定 = 一种 Unknown）。
- **U5｜只做注册模式够不够**（2026-09-17 新增）：注册模式今天就能交付，
  但它要求模型主动想起去调用。如果实测下来模型很少主动调用，
  那么“被动弹射”就不只是更优雅的形态，而是**必需**的形态。
  这是一个可以用真机实验回答的问题，别用讨论代替。
