# 01 · experience 的归属与分层

## 一、硬件层与具身（C1–C4）

**C1｜硬件层是伪需求。** experience 的耗时分布不在算术上：它省下的是 LLM 推理，
自己花掉的是进程 spawn、git、构建、网络。把经验执行写成 SIMD / CUDA 算子，
能优化的解释器开销在总量里几乎不可测。**用算子打 I/O 是在错的地方用力。**

**C2｜与硬件层唯一真实的关联是判据的质量上限。** 硬件层对 experience 的影响不是
“要不要写算子”，而是“证据能有多好”——噪声水平、观测时延、可逆性。
这三项决定判据族的上限，也决定 `Unknown ≠ True` 会在哪里频繁触发。

**C3｜具身不是特例，具身本质是一个特殊的 agent。** 只要 experience 的语义是
`(State, Intent) → 已验证转移 → State'`，动作空间是文件、是命令、还是执行器，
不改变经验的概念。具身与桌面场景的差别是三条**量级差异**而非范畴差异：
状态连续且带噪、可逆性经常不存在、时序有意义。

**C4｜实时控制环属于 agent 的动作空间，不属于 experience 层。**
1kHz 力控环是 agent 可以调用的**工具**（与“能跑 bash”同级的能力），
不是一条经验。经验层的证据是“技能执行完、结果被验证”这一级的，
不可能也不需要对一步 1ms 的动作留证据。**推论：experience 层永远不会被要求实时。**

> 这条修正了早期判断（“具身是唯一需要 kernel 的地方”）。修正后的结论是：
> 拿硬件层当作 experience 的深化方向，整体是伪需求。

## 二、归属：属性，不是协调器（C5–C8）

**C5｜experience 不是 agent 的协调器。** 它不影响不同 agent 之间的分工合作，
也不参与各 agent 如何完成自己的具体事情。把它放在“上层控制器”的位置是错位。

**C6｜experience 是某个 agent 的属性。** 该属性由两部分构成：
**先天经验**（预埋、随 agent/模型出厂）与**后增经验**（运行中自然生长）。

**C7｜这个定性同时容纳两条路径。**

| 路径 | 对应部分 | 含义 |
|---|---|---|
| 职业路径 | 先天经验 | agent 出厂即具备的标准作业能力，像学历与职业训练 |
| 进化路径 | 后增经验 | 在具体环境里长出的个体化能力，随使用改变 |

两者不是同一件事的两个阶段，而是**并存的两种来源**：厂商下发的基线能力，
与个体长出的适配能力。

**C8｜段化与属性化是同一个设计的两面。** 这不是巧合：

- 如果经验的单位是**一整条路径**，那么必须有人先决定“这条任务走哪条路”，
  这个决定只能由 agent 外部的控制器来做；
- 如果经验的单位是**段 + 前沿**（见 02），那么站在前沿并继续下去的主体
  天然就是 agent 自己——experience 就只能是它的属性。

**附带观察（记账用）**：这解释了为什么 `core-principle.md` 里“拥有调用权、
不拥有 Agent”的外层控制器思路，与 codex-main 里内嵌 Action Gate 的思路，
是**两种归属模型**，不是同一条路线的先后阶段。属性化选择了后者。

**2026-09-16 收口：不是冲突，是递进。**

| | lvl1（已建成） | lvl2（本目录讨论） |
|---|---|---|
| 形态 | experience 作为 agent **之外**的插件层 / 外部控制器 | agent **原生吸收** experience 作为它的属性 |
| 为什么是那样 | agent 内部架构不可编辑，改了就不能用 | 假设架构可改（原生 harness） |
| `core-principle.md` 的地位 | **项目建设契约**，不受本次讨论影响 | 不适用（它约束的是 lvl1） |

即：lvl1 是**被约束逼出来的正确解**，lvl2 是**解除约束后的进阶形态**。
本目录只讨论 lvl2。

## 三、三层经验与生命周期（C9–C11）

先天 / 后增是两分，展开后实际是三层，**生命周期规则各不相同**：

| 层 | 来源 | 验证强度 | 适用域 | 坚守程度 |
|---|---|---|---|---|
| 先天（通用） | 厂商，随模型版本回归 | 强（可大规模测试） | 宽 | **绑定模型版本**，可整体换代 |
| 预设（行业/场景） | 厂商面向目标用户群 | 中（可在基准环境回归） | 窄（行业/工具/平台） | 绑定行业域与外部系统版本 |
| 后增（个体） | 用户运行轨迹 | 弱 | 最窄 | 廉价、可弃、不被过度信任 |

**C9｜先天经验的生命周期绑定模型版本，而不是绑定用户。** 厂商能随 LLM 更新
重新测试与调整这部分——这意味着先天经验在性质上更接近**模型的一致性测试集**：
它回答的是“这个模型 + harness 出厂应当可靠地做到什么”。
它的维护动机与任何 SDK 厂商维护测试集的动机同源。

**C10｜预设经验是厂商供给目标用户群体的解决方案**，介于先天与后增之间：
验证强度接近先天，但适用域窄得多，因为它的成立依赖特定行业与外部系统。

**C11｜“灵动”体现在生命周期，不体现在适用域。** 后增经验可以更灵动、不必非常坚守，
但灵动必须落在“**易于产生、易于合并成段、易于丢弃**”上，
**不能**落在“适用域放宽”上。理由：放宽适用域会直接破坏 `Unknown ≠ True`
与“Unknown 不允许执行”这条安全不变量。安全的做法是后增经验从**窄**开始，
由证据逐步扩域，而不是从宽开始由反例收窄。

## 四、身份与分叉（C12–C14）

**C12｜总 agent 持有枝干主经验通路，子经验按情况分叉。**
agent 内部可以把处理不同任务的子 agent 划分为**对应身份**，或只给**不带身份的标签**。
主干通路由总 agent 持有；子经验在分叉处选择去向。

**C13｜身份与标签的职责必须分开，且身份要少而稳。**

| | 身份（identity） | 标签（tag） |
|---|---|---|
| 数量 | 少而稳 | 多而廉 |
| 承载 | 能力边界、权限边界 | 语境、路由 |
| 能否启用能力 | 可以 | **不可以**，只能排序 |

**理由（2026-09-16 修正）：主因是识别可靠性，不是权限。**
层级划分对应的是“总体指令 — 具体执行”的差异：越靠中枢，识别时可用的上下文越少。
所以**与其它经验路径高度重合的细节经验不能放在中枢自动执行**——
细枝末节的偏差会直接导致识别的完全错配（蝴蝶效应），
而误识别的代价约等于**机械执行的前缀深度**（与 C18 合起来读）。

- **第一指令区 = 识别唯一（或到第一个分叉点的距离足够远）的区域**——结构性定义，可计算；
- **重叠不等于不能执行**：重叠点之前的共同前缀在所有候选下都成立，仍然可执行；
  只是重叠点之后不能由中枢单方面选择；
- 权限规则（身份少而稳、标签只能排序不能启用）是**从上一条推出的结果，不是理由**：
  中枢不该选身份，根本原因是**中枢没有识别它的信息**，而不是它没有权限。
  **无身份的标签只能影响“选择先后”，不能影响“能不能执行”**（与 C27 同一条规则）。

**C14｜经验池按身份键控，并沿主干继承。** 主干段对全部子身份可见；
分支段只对匹配身份/标签的子 agent 可见。这要求一个继承式的可见面，
而不是单一扁平索引。

**待确认（C13 的推论，尚未经确认，不作为结论使用）**：
把“识别的不确定性”并入既有的三值语义——即 **Unknown 不止适用于前提，
也适用于“我现在处在哪个已知情境”**。若成立，则高重叠经验不需要任何额外规则，
就会被现有的“Unknown 不允许执行”挡在中枢自动执行之外；
而“第一指令区”可以精确定义为“识别唯一，或到第一个分叉点的距离足够远”。
