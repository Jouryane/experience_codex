# 09 · 两条腿的架构：Pull 与 Push

> 2026-09-17。由甲方的双 mode 提案 + 架构图评估收敛而来。
> 本文件是 lvl2 的具体架构方案，不是讨论记录。

## 一、命名：Pull 与 Push（C49）

“Explicit / Implicit”能用，但 Implicit 容易被读成“偷偷发生”。
更准确的一对词是**谁发起**：

| Mode | 谁发起 | 现有座位 | 今天的可行性 |
|---|---|---|---|
| **Pull**（原 Explicit） | **模型**发起调用 | 动态工具（`dynamicTools`） | **已实测可用**（见 08 §4.1） |
| **Push**（原 Implicit） | **世界状态**发起，不经模型 | 尚无 | 缺一个原语 |

**C49｜两条腿的差别只有一处：进入执行器的那个箭头从哪里来。**
执行、验证、学习三者完全共享。这是“experience ≠ dynamic tool”的精确表述：
**动态工具是一种表面（surface），experience 是一条已验证转移，而它有两个人口。**

## 二、修正后的架构图

甲方原图的问题：两条腿在 “World State” 处汇合，且 LLM 直接指向 World State——
这暗示**是 LLM 在干活**。实际上两条腿的执行者**都是 Experience 执行器**。

```text
                        EXPERIENCE REGISTRY
                               │
                     verified transitions
                               │
                 ┌─────────────┴─────────────┐
                 ↓                           ↓
        Pull Projection              Push Trigger
   （可命名、可被理解的表面）      （可判定、可自主成立的前提）
                 │                           │
        surface as Dynamic Tools      evaluate on world-state change
                 │                    三值门控：Unknown 不放行
                 ↓                           │
           LLM（选择 + 传参）                │
                 │  item/tool/call            │
                 └─────────────┬─────────────┘
                               ↓
                    EXPERIENCE EXECUTOR          ← 同一条执行路径
              （策略 → 围栏 → 备份 → 执行 → 判据）
                               ↓
                          World State'
                               ↓
                          Verification
                               ↓
                        Learning Trace
                               ↓
                      EXPERIENCE REGISTRY
```

与原图的五处差别，每一处都是承重的：

1. **汇合点从 World State 移到执行器**——LLM 不执行，它只选择与传参；
2. **两条入口箭头分别标注了各自的门**——Pull 需要“可命名”，Push 需要“可判定”；
3. **Push 入口明确写三值门控**（`Unknown` 不放行），这是实验里最便宜的保险；
4. **失败没有画成顺流而下**。Push 失败时**没有人可以交接**——这是真正未解的点，
   不该被一条向下的箭头掩盖；
5. **幂等是隐含前提**。两条腿都可能在同一个状态成立时各自触发；
   靠 C44（前提被自身动作证伪）保证不会双执行，图里应显式写出。

## 三、Pull 不是过渡品，是永久的互补（C50）

这是本轮最重要的推论，也是原提案需要修正的一处。

| Mode | 对转移的要求 |
|---|---|
| Pull | 模型能**看懂描述**并**给出参数** |
| Push | 前提能被**谓词判定**（可观测、三值、可自证伪） |

两者的要求不同，因此**存在只能 Pull、永远不能 Push 的转移**：
触发条件是语义的而非可观测的（例如“用户想要季度报表”，而不是
`billing/ledger.csv` 存在）。这类转移可以注册成动态工具，但永远无法自动触发。

**C50｜所以 Pull 不是“先做出来给 Push 铺路”，而是语义触发类的唯一形态。**
执行顺序上先做 Pull 是对的；但把它叙述成过渡品会低估它，也会在
Push 建成之后错误地把它降级。

## 四、对比表的两处修正与两行补充

原表七行基本可用，两处要改：

- “可以跳过 LLM reasoning”：动态工具 = “部分”——更准确的说法是
  **跳过的是“推导”，不是“观察”**（结果仍要回给模型）；
- “可以透明替代既有 tool”这一行，建议补一句注释：
  **这是全表唯一被运行时原语阻塞的一格，其余六行今天都可达。**
  这把表从“我们的野心”改写成“只有一格需要你”。

建议补两行，其中第二行是**唯一把 Experience 与另两者分开的行**：

| | Skill | Dynamic Tool | Experience |
|---|---|---|---|
| 幂等 / 可回滚 | 否 | 取决于实现 | **是**（备份 + 撤销） |
| 失败可分三层归因 | 否 | 否 | **是**（前提不成立 / 环境出错 / 转移失败） |
| **无模型参与时能否生效** | 否 | 否 | **是（Push）** |

## 五、待核对的两件事

1. **`deferLoading` 与 tool_search / discovery 的关系**：`deferLoading` 是
   `DynamicToolFunctionSpec` 上的**逐条字段**，不是检索索引。注册 1000 条经验时
   “只暴露相关的那几条”需要一个**发现面**——它是 Codex 已有的机制，
   还是我们要自己在客户端实现？**未核对，不要写进对外材料。**
2. **Push 失败时的归属**：Pull 失败可以回给模型；Push 失败没有接手方。
   候选答案：立刻停机 + 保留现场 + 留痕，等下一次模型请求时以事实形式告知。
   但这只是设计假设，**未经实验**。
