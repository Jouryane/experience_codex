# 11 · "拒绝昂贵"修复尝试与失败的方法论

> 2026-09-17，同日。承接 [08 §4.2](08-outreach-and-interfaces.md)。
> 原始数据：`active_leg/out/fix_results.jsonl`。

## 一、起因

08 §4.2 记录了一个失败模式：经验在"工作区已完成"时被再次触发，返回一句
"前提不成立"，模型于是自己去查、重新规划，代价很高。当时的记录是
**316,607 tokens / 59.8s**（对比首次执行的 87,665 / 21.7s）。

## 二、修法：补上三分规则缺的第四种情形

原设计里"前提不成立"一律当成失败。但实测暴露了第四种情形：
**前提不成立，原因是后置已经成立** —— 这不是失败，是 `ALREADY_SATISFIED`。

于是 `execute()` 增加一个分支：先看后置是否已成立，是则返回
`success=true` 加"后置已成立，无需动作"。这是设计层面的修正，不依赖统计。

## 三、对照实验（同一任务、同一已完成工作区）

| on-reentry | 返回语义 | totalTokens | wall | 模型调用次数 |
|---|---|---|---|---|
| terse | success=false，只有"前提不成立" | 89,170 | 23.3s | 1 |
| rich | success=false 加观测状态清单 | 153,231 | 34.6s | 1 |
| noop | success=true：后置已成立，无需动作 | 70,541 | 21.8s | 0 |

## 四、两个必须说清的结论

**结论一：§4.2 那个"3.6 倍"不成立，特此撤回。**
同一任务、同一返回行为（terse），08 §4.2 记到 316,607，本次记到 89,170。
它是单次高方差样本，不是效果。任何基于 n=1 的对比都不可用。

**结论二：原假设被证伪。** rich 比 terse 更贵（153k 对 89k），而且
outputTokens 与 reasoningOutputTokens 都接近翻倍（4289/2850 对 2289/1569）。
**多给状态信息没有让模型更快收手，反而让它推理得更多。**

## 五、真正学到的东西

1. **"已经满足"不是失败。** 这是唯一不依赖统计的改进；
2. **更长的拒绝信息可能反向激励推理。** 信息量不等于收敛速度 —— 这与
   "注入参考经验"那条老经验是同一类直觉错误；
3. **noop 的 0 次调用不能归因。** 它只说明"模型这次没调用"，不能说明是
   noop 行为导致的 —— n=1。

## 六、要作图，实验必须先重做

本轮**不可用于作图**。可用的设计是：

| 项 | 要求 |
|---|---|
| 样本量 | 每变体 n≥5（本轮 n=1） |
| 控制变量 | 固定任务文本、固定前置工作区状态、固定 thread 起始 |
| 未控变量 | 模型调用工具之前的**探索量**：本轮通知数在 668 到 8332 之间波动，这一项本身方差极大，很可能是 token 差异的主因 |
| 记录字段 | total_tokens / 请求次数 / 工具调用次数 / wall_s / verified |
| 判读纪律 | 差异必须跨样本稳定；单次差异一律视为噪声 |

**一句话**：这一轮最有价值的产出不是那三个数字，而是**先撤回自己的数字** ——
它避免了把一张建立在 n=1 上的图表拿去做论证。
