# 为什么 Agent 之上还缺一层：我们把它叫 3.5 层

> 这是一篇定位长文，写给做过 Agent 的人：我们为什么不再做一层 Agent，
> 而是做了 Agent 与应用之间的**可验证执行层**。

## 1. 一个大多数人遇到过的场景

你让 Agent 做一个已经做过很多次的任务：准备项目的标准文件、跑一遍发布前的检查、
把某个模板套到新目录里。它做完了，你也检查不出明显问题。

三天后，同样的话再说一遍，结果**不完全一样**：文件顺序变了、某个字段漏了、
它换了一种写法。你没法解释为什么，也没法回到上一版——因为唯一的证据是那段对话，
而对话不构成证据。

这不是模型不行。这是**Agent 层缺了一层东西**。

## 2. 四层结构里的空位

| 层 | 负责什么 | 现状 |
|---|---|---|
| 1 硬件 | 算力、设备、执行物理动作 | 成熟 |
| 2 LLM | 推理、生成、理解 | 成熟且拥挤 |
| 3 Agent | 工具调用、多步执行、编排框架 | 成熟且拥挤 |
| 4 AI 应用 | 面向业务的产品形态 | 快速发展 |
| **3.5 ？** | **把可验证的结果固化、执行、留痕、回滚** | **空位** |

为什么空位在这里？因为 3 层解决的是**“能不能做”**，4 层解决的是**“给谁用”**，
而中间那个问题——**“做过的、确定的做法，能不能每次都一样地做出来，并且可查可退”**
——一直没人专门负责。

结果是每个应用团队都在自己重写这套东西：埋点、日志、幂等、回滚、权限、审核。
写得好的团队得到了一套私有基建，写得一般的团队得到了一堆“看起来能跑”的脚本。

## 3. 3.5 层的四个硬指标

我们用它来定义这一层，也用它来验收自己：

1. **可复现**：同样的任务，走的是同一套步骤与参数，而不是重新推理一遍；
2. **可审计**：每一步都有证据与流水（执行 / 委派 / 回滚 / 设置变更）；
3. **可回滚**：写操作前有备份，任何一次运行都能按快照撤销；
4. **可控**：越界路径、危险命令、未授权动作在**副作用发生之前**被拒绝。

这四条听起来不像“AI 能力”，更像个基础设施——**这正是它是 3.5 层而不是 3 层的原因**。

## 4. 我们怎么做的（三个决定）

### 决定一：经验不是提示词，是执行体

大多数“让 Agent 记住”的方案，最后落到提示词或检索上下文：告诉模型“上次是这么做的”。
我们落的是**预编译步骤**：写入、追加、复制、移动、删除、受控命令，每步都是可执行、
可校验的。命中之后不是“建议模型这么做”，而是**直接做完**。

### 决定二：先动手，后委派

一个任务里，通常一部分是已知的、机械的、可验证的；另一部分需要判断。
我们让前者在进程内完成并留下证据，然后把**原任务 + 已完成状态 + 回滚指令**
交给 Agent，让它专注在剩下的判断上。

这样做的直接结果：省 token、省时间，且失败能分层归因——是“前提不成立”
（不扣经验的分）还是“环境出错”。

### 决定三：判据必须来自注册表，未知就是不执行

我们不接受“看起来做完了”。完成判据必须来自可观测来源：
文件存在性/内容/大小/哈希、目录、进程退出码、标准输出关键行、
git 状态、HTTP 状态、端口监听。

三值语义贯穿全程：**Unknown ≠ False ≠ True**。没有观测到的判据一律视为 Unknown，
而 Unknown **不允许执行**。这听起来保守，但它是这一层能被称为“可验证”的前提。

## 5. 一个真实的执行序列

```text
任务：给这个仓库做发布前检查
 ├─ 命中经验（ACTIVE）
 ├─ 策略校验：写=仅工作区；删除=关；命令=白名单(git, cargo)
 ├─ 备份：即将改动的文件 → backups/<session>/run-<ts>/
 ├─ 执行：git.dirty → cargo test --quiet → 检查 CHANGELOG 存在
 ├─ 判据：process.exit_code:exec#1 == 0  → True
 ├─ 留痕：experience_execution(success) / delegate / backup_restored
 └─ 委派：把“已完成 + 已验证”的部分交给 Agent，只让它判断剩余部分
```

出问题时：`POST /api/backups/<session>/restore` 一条命令回到执行前。
或者直接在设置页点「撤销」。

## 6. 为什么放在 Agent 之外，而不是改 Agent

我们刻意**不改 Codex/任何 Agent 的内部**：

- 密钥、审批、沙箱仍由 Agent 自己管理，我们不读密钥；
- Agent 只是可插拔执行器，今天用 Codex，明天换别的也不用重写经验；
- 我们只做三件不侵入的事：补一段“已完成部分”的事实说明、拦截自己范围内的步骤、
  记录轨迹用于学习。

好处是**可以立刻用**：接上就能用，不用等 Agent 生态改协议；也不用担心被某个
框架锁死。

## 7. 我们公开的边界（这一层最容易被过度承诺）

诚实是这一层的技术前提，所以我们把限制写在最显眼的地方：

- **匹配目前是子串匹配**，否定句会误命中——已登记为可替换点；
- **冷启动**：新装没有活跃经验，价值随使用累积；
- **只能负责可判定、可界定、可归因的工作**，判断类工作它做不了，也不该做；
- **不可观测的结论一律拒绝执行**——所以“能自动的活”比想象中少；
- 单机单用户、并发多会话是已知边界。

我们把每一条都写成了带升级路径的契约（见文末），而不是藏在文档角落。
**因为我们相信，这一层的说服力来自“它敢拒绝”，不是“它什么都能做”。**

## 8. 这一层对谁有用

| 角色 | 价值 |
|---|---|
| Agent 框架/工具开发者 | 拿到一份可直接落实的“可验证执行”契约，而不是再写一遍 |
| AI 应用/平台团队 | 把日志、幂等、回滚、权限收敛到一层，应用只关心业务 |
| 强合规/高风险场景 | 监管级留痕＋副作用前拒绝（金融、医疗、工业） |
| 具身与自动化 | 把标定例程、技能参数、故障恢复剧本变成可复现模板 |

两个行业场景的具体展开见 [产品总览](product-overview.md) 第 9、10 节。

## 10. 结论

LLM 让机器会思考，Agent 让机器会行动。**3.5 层让机器“做过的事”变成可靠的资产。**

我们不想再做一个更聪明的 Agent。我们想让每个团队都能把已经验证过的做法，
变成可复现、可审计、可回滚的执行体——**然后放心地让 Agent 去处理真正需要判断的部分。**
